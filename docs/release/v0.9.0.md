# csrf-sec v0.9.0 - Release Candidate

**An independent adversarial review, and every finding fixed test-first.** For v0.9.0 a reviewer with no part in the code was asked to break it: read the design, the API, and every source file, and find any way to get a request through that should not pass. They found none: no way to make `verify` or `check` accept a request built without the key or the victim's token, and they confirmed the MAC input, the decoder, the check order, the tag comparison (in the generated assembly for four targets), the time arithmetic, the key ring, the origin parser, and the redaction of secrets. They did find one medium and several low issues. Each one is fixed here, and each fix came with a test that failed first (`tests/review.rs`).

## Security

- **One session could fill the one-time store (medium).** An attacker's own session, a guest session is enough, could submit its own valid one-time tokens until `MemoryStore` was full, after which every other user's one-time actions were refused for up to twelve hours; each refusal also scanned the full shard under its lock. Now each session may hold at most 64 records at once (`with_session_limit`), a session's records live in one shard, a full shard with nothing expired refuses in constant time, and one-time tokens have their own lifetime of one hour by default (`Builder::once_lifetime`), so records last an hour and a minute, not twelve hours.
- **A malformed own origin turned the origin check off.** A trailing slash in configuration (`https://example.com/`) made the `Origin` and `Referer` checks pass everything to the token. A malformed own origin now matches nothing.
- **A malformed `Referer` slipped through when nothing was configured.** It is now refused, as the documentation already said and as `Origin` already was.
- **A clock stepping back across a restart.** `MemoryStore::new` now starts one minute ahead of the clock, so a step back of up to a minute cannot let a used token pass again; a clock before 2020 makes the store refuse everything instead of turning its restart protection off.
- **Milliseconds where seconds were meant.** A retire time in milliseconds kept a retired key valid for centuries, and `purge_expired` in milliseconds forgot every used nonce. Times past the range a token can reach now fail closed (`Error::InvalidRetireTime`, `Error::Clock`, or no purge).

## Changed

- Rotation keeps the old key one second longer, through the last valid second of a token a peer up to the skew ahead could have signed.
- `MemoryStore`: size it at 64 times the session limit or more (4,096 for the default), since a session's records share a shard.
- The subkey comparison used for promotion no longer copies key material into an unwiped value, and the unsent half of each MAC output is wiped.

## Documentation corrected

The review also caught text that sounded right and was not:

- The MAC does not stop a planted session cookie. If an attacker can plant the session cookie, they can plant a session they hold a token for; the `__Host-` prefix and, in `Strict` mode, the request policy are what stop that. The cookie guidance and the "no server-side session" recipe now say so, and `tests/review.rs` shows the attack passing in `TokenOnly` and refused in `Strict`.
- Adapters must pass the effective method after any override, and never let an override turn a safe method unsafe.
- `policy()` returning `Ok(NoFacts)` is not a pass; gate with `check`.
- A forger can choose to be reported as `malformed` or `unknown_key`, so detection layers should score every non-benign reason, not only `bad_mac`.
- The literal keys in examples are public placeholders.

## Added

`Builder::once_lifetime`, `Csrf::once_lifetime`, `DEFAULT_ONCE_LIFETIME`, `MemoryStore::with_session_limit`, `StoreError::SessionLimit`, `Error::InvalidRetireTime`, and `NonceUse::new` for testing custom stores.
