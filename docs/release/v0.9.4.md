# csrf-sec v0.9.4 - First Integration

**What the first integration taught the adapter guide.** web-net's CSRF step and gatekeeper-io's sign-in both depend on csrf-sec from crates.io now. Reading the two against each other needed no change to csrf-sec's API, and found two things its guide did not say. Nothing the crate does has changed.

## Documentation

- **A scope left out reads as a forgery.** A token issued with a scope and checked against a binding without one fails as `bad_mac`, the same as a forgery: the scope is inside the MAC and never written into the token, so the verifier cannot know there was one. When two layers check the same request (a framework's CSRF step and a gate's own login check, say), they must use the same binding, scope included, or the outer layer must leave the route to the inner one. The `BadMac` reason, `Binding::scope`, and the reason table say so too.
- **`policy`, then `verify`.** An adapter whose token arrives in a body it reads only after the origin check runs `policy`, reads the body, then `verify`. For an unsafe method and a plain binding that gives exactly what `check` gives in `Strict`; the adapter guide now says so.

## Added

- A property test holding that split equal to `check` in `Strict`, over realistic and random headers, valid and tampered tokens. With the `policy` step removed it fails on the first case.
