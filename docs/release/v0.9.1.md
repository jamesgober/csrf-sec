# csrf-sec v0.9.1 - Audit and OWASP Alignment

**The 1.0 audit, a point-by-point check against OWASP, and optional expiry.** This release stays on the 0.9 line: 1.0 will come after the first real integration and the rest of the checklist in `dev/ROADMAP.md`. Everything here is additive.

## Optional expiry

OWASP's cheat sheet treats a CSRF token as tied to the session, not as an access token with its own expiry. csrf-sec expires tokens after twelve hours by default, which caps how long a leaked token is any use; now that is your choice:

```rust
let csrf = Csrf::builder().key(KeyId(0), key).no_expiry().build()?;
```

With `no_expiry`, a token lives as long as the session id it is bound to, and your session layer ends it (a new session id at login, the session ended at logout). The issue time is still checked against the skew, so a token from the future is refused; rotating the key still retires old tokens one lifetime plus skew later; one-time tokens always expire. `Csrf::expires()` reports the setting.

## Checked against OWASP

Every point of OWASP's Cross-Site Request Forgery Prevention Cheat Sheet was compared with the crate. The design is the pattern it recommends for stateless servers (a signed token bound to the session, the session id never in the token, a constant-time comparison), with Fetch Metadata first and `Origin` then `Referer` as the fallback, `Origin: null` never trusted, missing headers never taken as same-origin, one-time tokens for sensitive actions, and login forms bound to the pre-login session. Two differences are deliberate and recorded (PLAN D-088, D-089). The guidance OWASP gives to the application around the library is now in the docs: `Vary: Sec-Fetch-Site, Origin`, which forwarded headers to trust, why `allow_same_site` trusts a taken-over subdomain, HTTPS with HSTS, attaching the token only to your own origin, and client-side CSRF, which no token stops.
