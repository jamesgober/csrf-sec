# csrf-sec v0.2.0 - Design Lock

**The API and the token format, written down before the code.** v0.2.0 locks the public surface of csrf-sec in `docs/API.md` and answers every open question from the plan. There is still no functional code in this release; it lands from `0.3.0`.

## What is csrf-sec?

<strong>csrf-sec</strong> answers one question for every state-changing request: did this request come from our own page, for this session? It answers with three independent checks: a request origin policy over the browser's Fetch Metadata and `Origin` headers, a signed token bound to the session and masked differently on every response, and cookie guidance for the session cookie. It is protocol-free and stateless, and verification allocates nothing and takes no lock.

## The API in three calls

```rust
let csrf = Csrf::new(key)?;
let token = csrf.issue(session_id)?;               // 59 characters, different on every call
csrf.check(&facts, session_id, submitted)?;        // request policy + token
```

Tier 2 adds a `Binding` (scope, previous session, one-time store) and a builder for keys, lifetime, skew, mode, and allowed origins. Tier 3 takes the time and the randomness source explicitly and works without `std`.

## Decisions that changed the original plan

- **Canonical MAC input.** The plan concatenated the session id and the scope with no lengths, so two different bindings could produce the same MAC input. Both are now length-prefixed with varints (D-008).
- **Domain separation in the key.** One subkey per key id and token kind is derived at construction, and the application key is not kept. Dropping the text prefix from the MAC input keeps a typical session id inside one BLAKE3 block (D-009).
- **One-time tokens check the MAC before the store.** A one-time token is a signed token with a 128-bit nonce. Forged requests are refused before the store is touched, so an attacker cannot burn a user's one-time token or load a shared store (D-011).
- **Fail closed on issue.** `issue` returns a `Result`: if the OS random generator or the clock fails, no token is minted and nothing panics. The token is an inline buffer, so issuing allocates nothing (D-015).
- **Constant-time codec.** The base64url codec uses arithmetic instead of lookup tables and accepts only canonical text, so a changed character can never still verify (D-013).
- **Two-step key rotation for clusters.** Keys can be accepted (verify only) before any node signs with them (D-017).
- **Accurate reasons.** `NotYetValid`, `Unverifiable`, `AlreadyUsed`, and `StoreUnavailable` join the list; a forgery can never lower its own severity (D-012).

The full list is D-008 to D-026 in `dev/PLAN.md`.
